Why Do Reasoning Models Cost More to Serve Than Standard LLMs?

The price per token is often the same. The difference is how many tokens a reasoning call writes, and what those tokens do to GPU memory and scheduling.

November 1, 2026

The short version: a reasoning call usually costs more because it writes more tokens, not because each token has a higher price. Hidden reasoning is billed at the output rate on OpenAI and Google. On the GPU, those tokens add decode steps, keep the KV cache resident for longer, and make request length hard to predict. For RLMs, the dollar effect is smaller than the latency effect, because sub-call input usually outweighs sub-call output.

Do reasoning tokens have a higher price?

Mostly no. The label "reasoning model" also means less than it did. DeepSeek's pricing page lists no separate reasoning model and says each model "supports both non-thinking and thinking (default) modes." OpenAI's reasoning guide lets you set effort on one model, and gpt-6.1-sol rejects both none and minimal.

The bill comes from the count. OpenAI says reasoning tokens "are not visible via the API" but are "billed as output tokens." It reports them as reasoning_tokens under output_tokens_details. Google's Gemini pricing page labels the row "Output price (including thinking tokens)."

List prices are a weak guide to this question. OpenAI's pricing page, read November 1, 2026, still shows o1 at $60 per million output tokens and gpt-4o at $10. It also shows o3, a reasoning model, at $8. So a reasoning model does not have to carry a higher rate. A 2026 study of ten LLMs on embedding-style tasks, The Embedder's Dilemma, reports that "reasoning tokens account for 28 to 81% of LLM inference cost." That range comes from those tasks and models, so do not apply it to every workload.

Why does a longer output cost more on the GPU?

Output is sequential. The model makes one token per decode step, and each step needs the token before it. Our post on prefill vs decode explains the mechanics. For cost, the result is simple: reasoning tokens add steps, and each request stays on the GPU for all of them.

The best public measurement here describes energy, not dollars. Vellaisamy et al. model each request as a fixed prefill and setup cost plus a marginal cost for each output-token step. They tested this on NVIDIA H100 and H200 GPUs. Longer outputs lowered energy per token and raised total request energy. That split explains why cost per token can fall while cost per request rises. Batching lowers token energy too, but the benefit shrinks as context grows.

One caution: the gap between input and output price is a vendor's choice. None of the vendor pages we read gives a cost to serve, so a price list does not measure the hardware.

How does long reasoning tie up KV cache memory?

The cache grows with every generated token, and it stays in memory until the request ends. Pascal (Cho et al., 2026), a scheduler built for reasoning models, states the limit: the number of requests in a batch is "constrained by the cumulative KV cache footprint." Under first-come, first-served, "once a request starts reasoning, it holds GPU memory until its answering phase completes."

This cost grows faster than the token count. Memory held over time is roughly steps × (prompt + steps/2), which we call token-steps. That is our arithmetic, not a measured figure. With a 4,000-token prompt:

  • 500 output tokens: 500 steps, about 2.1 million token-steps, 4,500 tokens of cache at the peak.
  • 4,740 output tokens: 4,740 steps, about 30.2 million token-steps, 8,740 tokens of cache at the peak.

You pay per token, but the GPU pays per token-step. Per-sequence memory for a given model comes from the formula in our KV cache post. A GPU's rate in tokens per second need not fall. Requests per second do fall, because each request needs more of those tokens.

Why does unpredictable length hurt scheduling?

A scheduler admits a request before it knows how long that request will run. Pascal's authors call reasoning lengths "highly variable." In their AlpacaEval2.0 and Arena-Hard traces, more than 70% of requests made fewer than 1,000 reasoning tokens. On problem-solving benchmarks (MATH-500, GPQA, LiveCodeBench), reasoning tokens reached as much as 8.48× the answer tokens.

Mixed lengths cause head-of-line blocking, where a short request waits behind long ones whose caches stay resident. Pascal measured DeepSeek-R1-Distill-Qwen-32B on vLLM with KV cache memory capped below what the workload needed. First-come, first-served raised latency for short reasoning requests by up to 5.14× over an oracle baseline. Round robin raised latency for long requests by up to 1.75× over the same baseline. In a cluster simulation, Pascal's phase-aware design cut tail TTFT by up to 72% against first-come, first-served, and throughput stayed within 3%. So scheduling recovers latency, but the paper gives no such gain in raw capacity.

When memory runs out, the scheduler can offload a request's KV cache to CPU memory and suspend it. Vendors face the same length problem from the other side. OpenAI recommends "reserving at least 25,000 tokens for reasoning and outputs" when you start.

What does a reasoning call cost in dollars?

Here is a worked example at gpt-6.1-sol standard rates: $2 per million input tokens and $10 per million output tokens, from OpenAI's pricing page, read November 1, 2026. The token counts are assumptions. This model does not accept none, so the first row is a baseline for the arithmetic, not a setting you can select. Each call has 4,000 input tokens and a 500-token visible answer.

  • No reasoning tokens: $0.008 input + $0.005 output = $0.013.
  • 800 reasoning tokens (assumed): 1,300 output tokens. $0.008 + $0.013 = $0.021.
  • 4,240 reasoning tokens (assumed, the 8.48× upper figure from Pascal): 4,740 output tokens. $0.008 + $0.0474 = $0.0554.

The time view uses the same counts. At Pascal's 100 ms per-token target, those calls decode for 50, 130, and 474 seconds. The input bill never moves. Reasoning takes about 38% of the bill in the middle row and 77% in the last.

What does this mean for RLM sub-calls?

An RLM has a different token shape. It holds a long prompt in an external environment and calls itself on pieces of it, so each sub-call reads a lot and writes a little. Take 50 sub-calls of 20,000 input tokens, each with a 200-token answer, at the same rates. These counts are also assumptions.

  • No reasoning tokens: $2.00 input + $0.10 output = $2.10.
  • 800 reasoning tokens per sub-call: $2.00 + $0.50 = $2.50.
  • 1,696 reasoning tokens per sub-call (8.48× the answer): $2.00 + $0.948 = $2.95.

Input still holds most of the bill, so the dollar effect stays modest. The time effect is larger. At the same 100 ms target, each sub-call goes from 20 seconds of decode to 100 or about 190. A parallel fan-out finishes only when its slowest sub-call does, so variance in reasoning length sets your wall time. Three practical rules follow.

  1. Set a low effort on sub-calls. Most sub-calls extract or classify one snippet. The Embedder's Dilemma found that lower reasoning budgets "preserve or improve retrieval quality for most models" in its ablation. Our post on thinking tokens and accuracy covers the evidence, so sweep the setting on your own tasks.
  2. Be careful with hard caps. If a call reaches max_output_tokens, OpenAI says it "could incur costs for input and reasoning tokens without receiving a visible response." In an RLM, a retry then pays the full input again.
  3. Watch depth. Reasoning cost scales with the number of calls. Wang's reproduction found that depth 2 "exponentially inflates execution time (e.g., from 3.6s to 344.5s) and token costs." For the wider case for spending compute at inference time, see inference-time compute scaling.

The bottom line

Reasoning models cost more to serve because they write more tokens per request, and each token adds a decode step, more KV cache held for longer, and more length variance for the scheduler. The price per token is often the same. At the request level, track reasoning_tokens and not just the price per token. In an RLM, keep reasoning low on sub-calls, spend it at the root where planning happens, and measure the slowest sub-call, because that is where reasoning hurts first.

FAQ

Frequently asked questions

How do I see how many reasoning tokens I paid for?

On OpenAI, read the usage object in the response. The count is in reasoning_tokens under output_tokens_details. You cannot read the hidden tokens themselves, but you pay for them at the output rate.

Is a reasoning model always more expensive than a standard model?

No. OpenAI's pricing page, read November 1, 2026, lists o3 at $2 input and $8 output per million tokens, and gpt-4o at $2.50 input and $10 output. The total for a request can still be higher, because the reasoning model writes more tokens.

Does batching remove the extra cost of long outputs?

It helps but does not remove it. Vellaisamy et al. found that batching lowers energy per token, and that the benefit shrinks as context length grows. Each request also holds its KV cache for the whole run, which limits the batch size.

Do reasoning tokens use up the context window?

Yes on OpenAI. The reasoning guide says they occupy space in the context window even though you cannot see them. The max_output_tokens limit also covers both reasoning and visible output.

Should the RLM root use more reasoning than the sub-calls?

That is a sensible starting point, not a tested rule. The root plans and writes code, while most sub-calls do a narrow job on one snippet. Run an evaluation sweep before you fix the setting.
